# CLAUDE.md — Claude Code ⇄ Notion「AI外部脳」連携

このリポジトリは、Claude Code セッションを **既存の Notion 知識体系（FBSC ナレッジベース｜AI外部脳）** に接続し、
コード作業を含む「仕事のことすべて」をセッションを跨いで記録・継承するためのワークスペースである。

**Claude Code はセッション開始時に必ず本ファイルを読み、以後この規約に従って Notion を読み書きする。**
本ファイルは Notion 側の運用ルールの **コード側ミラー（要約・入口）** であり、**正本は Notion**（後述）に置く。
矛盾が生じたら Notion を優先し、本ファイルを更新する（二重正本を作らない）。

Notion への読み書きは **Notion MCP コネクタ**（本リポの `.mcp.json` で `notion` として宣言。
ツール名は `mcp__notion__*`。環境により `mcp__Notion__*` の場合もある）で行う。

---

## 0. 前提

- この Notion ベースを Claude の外部脳として扱い、セッションを跨いで知識を引き継ぐ。正本は Notion。
- 個人利用（SK の仕事ツール）であり、チーム共有は前提にしない。
- 本リポは「コード側」。ここでのコード作業（実装・調査・デプロイ）も Notion に記録し、コードと知識を一体で扱う。

## 1. 起動時読込（セッション開始時に必ず実行）

新しいセッションの冒頭で、Notion MCP を使い次を順に実行する。
**コスト効率化A**: Notion 検索・取得時は `max_highlight_length=0`・`page_size≤5` を既定とし、トークン量を最小化する。

1. **`00_AI運用ルール`（正本）と `Personal preferences保管ページ` を読む**（本ファイルはその要約に過ぎない）。
2. **今回の話題に関係するプロジェクトを特定する**（`プロジェクト一覧` DB の現行プロジェクトから判定）。
   本リポの作業は多くが **PP-AI駆動開発 / AEP** に該当する。
3. 該当プロジェクトの **`00_運用設計・背景` の冒頭「現在地サマリー」セクションのみ**を読む
   （全文読込は構成・運用の変更指示があったときに限定）。
   併せて **横断（ナレッジ基盤・全体共通）プロジェクトの「現在地サマリー」** も読み、進行中の横断施策と主要資料インデックスを把握する。
4. **`セッションログ` DB を プロジェクト=該当 で絞り込み、最新3件（検討経緯・結論・次アクション）を読む**。前回からの連続性を確保する。
5. 該当プロジェクトの **`Mistakes`** を読む（同じミスを繰り返さない）。
6. 質問のキーワードで **`MASTER_KNOWLEDGE`・`Decisions`** を検索し、ヒットした正本レコードを読む
   （Decisions は矛盾照合の準備も兼ねる）。用語の正誤・確定仕様など**誤答リスクの高い論点は検索必須**。
7. **論点が過去資料に関わる／参照名（「○○の資料」）で指された場合のみ**、`資料管理` DB をキーワード検索し、ヒットしたら Drive URL から実体を fetch する（常時検索はしない）。
8. **`学び・ナレッジ所在マップ`（索引）を横断参照の入口として使う**（保管先8箇所と検索経路の単一索引）。
9. 読み取った内容を踏まえて回答・作業する。
10. **新しい主張が `Decisions` の確定内容と矛盾する場合は、いつ・どのセッションで・なぜそう決めたかを提示してから先に進める**。

単発質問（例：今何時か）はスキップしてよい。

> 実行を省力化するなら **`/session-startup` スキル**（`.claude/skills/session-startup/`）を呼ぶ。

## 2. 書き込み（該当したらその場で書く）

「後で書く」はしない。会話・作業の流れの中で都度書き込む。
ただし **Notion への書込操作はユーザー承認（権限プロンプト）を経る**（`.claude/settings.json` で書込系は `ask`）。
書き込み前に「何を・どこへ書くか」を提示し、承認後に反映する。

| 書き込む対象 | 書き込み先 DB | 何を書くか |
|---|---|---|
| 知見・TIP | **MASTER_KNOWLEDGE** | バグ解決（原因＋解決策のペア）、ライブラリ/API/ツールの新発見、環境構築でハマって解決したこと。一般化できるものは 種別=TIP |
| 決定 | **Decisions**（AEP では Decision Log D-001…） | 複数の選択肢から1つを選んだ判断（A vs B・なぜA）、設計・方針の決定 |
| 失敗と是正 | **Mistakes** | 第5節の3条件を満たす訂正のみ |
| 未解決事項 | **OPEN_ITEMS** | 次に解くべき論点・宿題 |
| プロジェクト状態 | **プロジェクト一覧** | 状態・バージョン・概要が変わったとき |
| ユーザーの好み | **Preferences** | 作業スタイル・好みの新発見 |
| 成果物＋ビルド仕様 | **資料管理** | 生成物の正本＋ビルド手順（コードの成果物もここ） |

### セッションログに書く（一段落ごと）
チャット/作業が **一段落した時点**（話題転換・検討終結・ユーザー満足表明・実装完了等）で、`セッションログ` DB へ1レコード追記する。

- `タイトル` = **日付＋主題**（例：`2026-07-21 Claude Code×Notion連携リポ`）
- `検討経緯` = 議論の流れ・出た選択肢・没案とその理由
- `結論` = このセッションで確定したこと
- `次アクション` = 次回セッションの出発点
- `ステータス` = 進行中 / 一段落 / 確定
- `前回との関係` = 継続 / 方針転換 / 矛盾解消 / 新規
- `日付` = セッション実施日
- 発生した **決定 / 未解決事項 / 関連資料** はそれぞれ `Decisions` / `OPEN_ITEMS` / `資料管理` にも**原子的に**登録し、`セッションログ` からリレーション（`関連Decisions`・`関連OPEN_ITEMS`・`関連資料`・`プロジェクト`）で紐付ける。
- 同時に当該プロジェクトの `00_運用設計・背景` の「現在地サマリー」を上書き更新する。

> 実行を省力化するなら **`/session-record` スキル**（＝「整理して」相当）を呼ぶ。

## 3. コード ⇄ Notion 連携の要点（本リポ特有）

- 本リポでの**コード作業（実装・調査・デプロイ・修正）そのものを Notion に記録する**。作業＝セッションログの1件、恒久知見＝MASTER_KNOWLEDGE、判断＝Decisions。
- **コミット/PR・生成物はセッションログの `関連資料` や `資料管理` DB に紐付ける**（コードと知識のトレーサビリティ）。
- Power Platform ソリューション作業では、`学び・ナレッジ所在マップ` に従い **SET-SOL-001（MASTER）＋ Mistakes DB ＋ AEP Development台帳 ＋ AEP Decision Log** を確認する（7-15）。
- **二重正本禁止（D-007）**: 外部/生記録は台帳に残し、確定ルールのみ SET-\* 規約へ写す。

## 4. 報告・透明性（必須）

Notion を読み書きしたら、**何をしたかを必ずユーザーに伝える**（例：「Notion: MASTER_KNOWLEDGE に TIP-007 を書き込みました」）。
**サイレントで読み書きしない。**

---

## 5. Mistakes 追記の3条件

ユーザーから訂正を受け、かつ次の3条件を**すべて**満たすときのみ `Mistakes` に追記する。
1. ユーザーからの**明示的な訂正**である（AI 自身の気づきではない）
2. **繰り返し起こり得るパターン**である（一度きりの偶発ではない）
3. 具体的な「する/しない」で書ける

プロパティ: `タイトル`=一言で何を間違えたか / `NG`=実際の間違い / `Correct`=次回からの正しい対応 / `Trigger`=適用状況。プロジェクトを必ず設定する。

---

## 6. プロジェクト分離・プロパティ規約・文体

- **プロジェクト分離（厳守）**: 各プロジェクトは別案件。フロー・仕様・アーキテクチャを混同しない。全レコードに `プロジェクト` リレーションを必ず設定する。横断知見は種別で示す。
- **プロパティ規約**: `1行要約` 必須 / `ステータス`=正本·下書き·要見直し（原則「正本」だけを根拠にする）/ `確認日` / `出典` / タグ・カテゴリは選択肢 / 本文は H2·H3＋3〜5行の短段落。
- **文体**: である調で統一。司会者口調・評価語先行・主語不在・締め定型句・教科書口調を使わない。根拠と結論を分けて書く。詳細は `ドキュメント生成ルール（マスター）` を参照。

---

## 7. Inbox「整理して」運用（Review モード）

ユーザーが `Inbox` に放り込み「整理して」と指示したら、各アイテムを次の3パターンで判定し、**いずれも実行前に提案し承認を得てから反映する**。
- (a) 既存プロジェクトに該当 → 該当プロジェクト紐付けで適切な DB へ移動（種別判定→1行要約生成→タグ付与）。
- (b) どの既存プロジェクトにも該当せず単発を超える → 新規プロジェクト作成を提案（名称候補・スコープ明示→承認→`プロジェクト一覧` 登録→配下に `00_運用設計・背景` 雛形（「現在地サマリー」必須）作成）。
- (c) 単発の知見・気づき・好み → `個人メモリ拡張` または `MASTER_KNOWLEDGE` への書き込み案を提示。

判定に迷う場合は判定案を提示してユーザー確認を取る。
